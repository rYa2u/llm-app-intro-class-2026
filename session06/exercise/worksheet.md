## コードの説明
- cosine_similarity()の計算を完成させ、仮のraiseを削除する。
- 自分が変更した行の意味：forで同じ位置の成分を取り出し、dotにa[i] * b[i]を加えて内積を計算する。a_sizeとb_sizeにはそれぞれ成分の2乗を合計する。最後に内積を両方の長さ（2乗和の平方根）の積で割る。仮のraiseを削除した。
- 計算例：[1,0]と[1,0]は1、[1,0]と[0,1]は0、[1,0]と[-1,0]は-1。向きが同じ[1,2]と[3,6]も約1になる。
- 境界の扱い：片方でもゼロベクトルなら教材の規則で0を返す。次元数が異なる場合はValueErrorにする。
- 登録時の流れ：init_db.pyで見出しごとの断片をDBへ登録 → build_index.py → build_embeddings() → embed() → ベクトルとモデル名をDBへ保存。
- 質問時の流れ：POST /api/ask → main.pyのask() → search_vector()で保存済みモデル名を確認 → 質問をembed() → 各断片とのcosine_similarity()を計算 → 正の類似度から上位件数を選択 → 元の本文をask_with_context()へ渡す → 回答と資料を返す。
- モデルの区別：資料と質問を同じモデルで数値化する。デモ用モデル名とAPI用モデル名は分けて保存し、異なるモデルのベクトルは比較しない。

## 確認問題への回答
1. 異なるEmbeddingモデルのベクトルをそのまま比較してはいけない。数値が表す座標の意味が一致するとは限らないため。資料と質問に同じモデルを使う。
2. 正答率80%ではない。ベクトルの向きの近さを表す数値であり、回答の正しさの確率ではない。
3. 対処は必要。意味が近い資料でも答えが含まれない場合があるので、本文と出典を確認し、根拠が足りなければ回答を控える。
4. python init_db.pyで資料DBを更新し、python build_index.pyでベクトルを作り直す。モデルやデモ/APIモードを変えたときも再作成する。

## 失敗と改善
- 失敗した操作・入力：ベクトル未作成の検索、デモのベクトルをAPIモードから使う検索、資料を再登録した直後の検索はいずれも400で止まった。
- 原因の予想：現在のモード用のベクトルがないか、保存したモデル名が一致しないため。資料再登録では古いベクトルが無効になる。
- 試した変更：デモでbuild_embeddings()を実行して10件保存すると検索できた。資料再登録後もベクトルを再作成すれば検索が復旧した。テストではモデル不一致時にAPIを呼び出さないことも確認した。
- 検索の失敗と改善：「ページを閉じても…」はデモで0件になったが、キーワード「ページ 閉じて データ 残る」なら該当資料を取得できた。デモの弱点から実際のEmbeddingの精度は判断できない。
- 検証：pytestでコサイン計算の同方向・直交・逆方向・長さの違い・ゼロベクトル・次元不一致、検索の並び、モードの区別、再登録後の再作成を確認した。
- まだ確かめていないこと：実際のEmbedding APIによる言い換え検索の成功例と失敗例、APIの利用量、生成回答の正確さと引用ID。実際の意味検索の比較実習は未検証。
